Technical Reference

Defensive Security Controls Architecture

Comprehensive breakdown of the defensive patterns, cryptographic specifications, and architectural controls implemented in the Secure Authentication Lab.

1. Argon2id Password Hashing
Password Hashing Competition (PHC) Winner

Unlike legacy hashes (MD5, SHA-256) which are fast and trivial to crack on GPUs, Argon2id is intentionally memory-hard. It resists both side-channel cache timing attacks (inherited from Argon2i) and massively parallel GPU/ASIC cracking (inherited from Argon2d).

Algorithm Memory-Hard? GPU Resistance Side-Channel Resistance
MD5 / SHA-256 No (0 KB) None (Billions/sec) None
Bcrypt 4 KB Moderate Good
Argon2id 64 MB (65536 KiB) High (ASIC Proof) High (Data-independent)
2. Timing Attack Mitigation
Constant-Time Dummy Verification

If an application immediately rejects a non-existent username in 2ms, but computes an Argon2id verification for a real user in 80ms, attackers can infer valid usernames using high-precision statistical timing attacks.

Our Defense: When a username does not exist in the database, the server executes hasher.verify(DUMMY_HASH, password) behind the scenes. Both valid and invalid user lookups consume approximately equal computation cycles.
if user is None: dummy_verify(password) # Equalize execution timing return GENERIC_LOGIN_ERROR, 401
3. Session Hardening & Fixation
Cookie Flags & Lifecycle Controls
  • HttpOnly: Blocks JavaScript access via document.cookie, preventing cookie theft in case of Cross-Site Scripting (XSS).
  • SameSite=Lax: Withholds cookies during cross-site requests, mitigating Cross-Site Request Forgery (CSRF).
  • Session Fixation Countermeasure: When authenticating, session.clear() wipes pre-login session states, forcing the browser to adopt a freshly signed cryptographic session identifier.
  • Inactivity Expiration: The server tracks session['last_active'] and forces re-authentication after 30 minutes of idle time.
4. Rate Limiting Architecture
Abuse Prevention & Storage Backends

Authentication endpoints are prime targets for automated credential stuffing and password spraying. We enforce a 5 attempts per minute limit per client IP using Flask-Limiter.

Storage Backend Comparison:
  • memory:// (Development): In-process storage. Fast, zero-setup, but lost on process restart and not shared across multi-worker WSGI processes.
  • redis:// (Production): Distributed in-memory data store. Persists rate limit counters across multiple load-balanced web servers.
5. Parameterized SQL Queries
Complete SQL Injection Neutralization

SQL injection occurs when untrusted input is concatenated directly into SQL command strings. In this lab, all queries are compiled using parameter placeholders (?).

# VULNERABLE (DO NOT USE): # cursor.execute(f"SELECT * FROM users WHERE user='{input}'") # SECURE (PARAMETERIZED): cursor.execute("SELECT * FROM users WHERE username = ?;", (input,))

The database driver treats parameter values strictly as literal values, never as executable SQL commands.

6. Server-Side Input Validation
Strict Whitelisting & DoS Mitigation

Client-side validation can be bypassed effortlessly with curl, Postman, or browser developer tools. Defensive systems mandate rigorous server-side checks.

  • Username Whitelist: ^[a-zA-Z0-9_]{3,30}$. Blocks control characters, path traversals, and script injections.
  • Password Upper Limit (128 chars): Prevents algorithmic Denial of Service (DoS) where an attacker submits megabytes of text to exhaust CPU/memory during Argon2id hashing.
  • Complexity Bounds: Minimum 12 chars with upper, lower, digit, and special characters.
